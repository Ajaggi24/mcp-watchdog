# MCP tool-change review benchmark

A small, labeled dataset of changes to MCP tool definitions, for measuring how well a tool **prioritizes** change review. Detection alone is trivial: any canonical hash catches every change.

| file | cases | notes |
|---|---|---|
| `cases/dev.json` | 40 | Labels written before any rules. The rules were developed against this set. |
| `cases/heldout.json` | 22 | Written after the v1 rules were frozen (`FROZEN_RULES_v1.sha256`), on new tools. Used to fix v2, so it no longer tests v2. |
| `cases/heldout2.json` | 20 | Written by a different author without reading the rules, after v2 was frozen (`FROZEN_RULES_v2.sha256`). The blind test for v2. |

## Case format

```json
{
  "id": "H14",
  "group": "noop | cosmetic | interface | sensitive | evasive",
  "label": "none | low | medium | high",
  "rationale": "why a reviewer would want this priority",
  "before": { "...MCP Tool definition, or null for a newly added tool..." },
  "after":  { "...MCP Tool definition (name, description, inputSchema, annotations, ...)" }
}
```

`label` is the review priority a careful reviewer would want. Every label except `none` still requires re-approval. The label only decides the order.

## Evaluate your own tool

Write a function that maps `(before, after)` to `none | low | medium | high` and report:

1. Changes needing review that you classed as `none` (this must be 0, or the gate weakens).
2. `high` cases you ranked `high`.
3. `low`/`medium` cases you ranked `high`.

`evaluate.py` shows how. The JSON is regenerated by `build_*_cases.py`, which also document each label.

Contributions of new held-out cases, especially ones written by people who haven't read the rules, are the most useful way to improve this.
